# Nabto Micro DATA packet structure and fan-change correlation

Date: 2026-11-19  
Branch: `remote-nabto-connection`  
Capture: user-supplied `genvex-fan-change-v3.pcap`  
Markers (Europe/Copenhagen, UTC+01:00):
- 15:17:28.403840563 FAN_SPEED_CHANGE
- 15:17:39.302684371 FAN_SPEED_CHANGE
- 15:17:50.445283095 FAN_SPEED_CHANGE

This is passive analysis of user-provided captures. Session identifiers, account identifiers, device identifiers, certificate contents, and cryptographic payload bytes are intentionally omitted.

## Executive summary

The three fan-change markers in this capture each have a 70-byte client-to-peer Nabto DATA packet shortly before the marker:
- 189 ms before marker 1 (sequence 100)
- 74 ms before marker 2 (sequence 123)
- 161 ms before marker 3 (sequence 144)

Each request receives a 24-byte `NOTIFY_MICRO_ACK` and a 70-byte DATA response. The server response follows the request by approximately 35–41 ms in this capture.

Across three distinct event windows at 15:08, 15:12 and 15:17 in a cumulative capture, all nine marked changes have a 70-byte request 74–385 ms before the manually entered timestamp marker. Each has a corresponding ACK and DATA response. This is a strong temporal correlation, but not proof that the 70-byte request contains the fan-speed write: the timestamp is entered after the user action, and other 70-byte requests also occur outside the marked events.

The packet layout can now be mapped against the public Nabto uNabto source. The 70-byte packet is:
- 16-byte Nabto packet header;
- 4-byte payload header;
- 2-byte crypto-suite code;
- 48-byte crypto data: 16-byte IV, one 16-byte AES-CBC ciphertext block, and 16-byte truncated HMAC-SHA256.

The plaintext in a 70-byte packet is therefore at most 15 bytes under the published PKCS#7 padding implementation. It remains encrypted; no plaintext command or fan-stage value has been recovered.

## 1. Parsed DATA packet layout

Offsets are zero-based from the beginning of the UDP payload.

| Offset | Size | Field | Interpretation |
|---|---:|---|---|
| 0–3 | 4 | NSI.cp | Nabto client-peer identifier |
| 4–7 | 4 | NSI.sp | Nabto server-peer identifier |
| 8 | 1 | Type | `0x16` = DATA |
| 9 | 1 | Version | `0x02` |
| 10 | 1 | Retransmission count | Observed as zero in these requests |
| 11 | 1 | Flags | `0x00` request; `0x01` response |
| 12–13 | 2 | Sequence | Big-endian packet sequence |
| 14–15 | 2 | Total length | Big-endian; `0x0046` = 70 |
| 16 | 1 | Payload type | `0x36` = CRYPTO |
| 17 | 1 | Payload flags | Observed zero |
| 18–19 | 2 | Payload length | Big-endian; `0x0036` = 54 bytes including the 4-byte payload header |
| 20–21 | 2 | Crypto code | `0x230A` |
| 22–37 | 16 | IV | AES-CBC initialization vector |
| 38–53 | 16 | Ciphertext | One AES block |
| 54–69 | 16 | Integrity value | Truncated HMAC-SHA256 |

The public uNabto source defines the packet header as 16 bytes and the payload header as 4 bytes. It defines DATA as packet type 22 (`0x16`) and CRYPTO as payload type `0x36`.

The crypto code `0x230A` is composed from the uNabto crypto flags for CRYPT + secret-key encryption + AES-CBC + HMAC-SHA256.

## 2. ACK packet layout

The 24-byte ACK is a 16-byte Nabto header followed by an 8-byte NOTIFY payload:
- payload type `0x34` = NOTIFY;
- payload length `0x0008`;
- 32-bit notification code `3` = `NOTIFY_MICRO_ACK`.

The public uNabto source documents this notification as: the Micro has received the request, but the answer is not ready yet. The ACK is not the application response; the later DATA packet is the response.

## 4. Crypto layout and plaintext size

The published uNabto implementation documents the encrypted form as:

`IV(16) + AES-CBC(padded plaintext) + truncated HMAC(16)`

For a 70-byte packet, the 48-byte crypto data is exactly:
- 16-byte IV;
- 16-byte ciphertext (one AES block);
- 16-byte truncated HMAC.

Under the published implementation's PKCS#7 padding, one ciphertext block can contain between 0 and 15 bytes of plaintext. The packet's plaintext is therefore very short, consistent with a compact request, but its application meaning is unknown.

The same source documents 96 bytes of DATA key material: two 16-byte AES keys and two 32-byte HMAC keys, with direction-specific key selection. The capture does not contain those keys in cleartext in the DATA packets. The source also shows that DATA crypto context is initialized from key material supplied by the GSP/connection setup; the 70-byte DATA packet itself is not sufficient to derive it.

## 5. Potential IV anomaly requiring confirmation

Across the three supplied captures, every server-to-phone encrypted DATA packet from the observed remote peer uses the same first 16 crypto-data bytes:

`00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f`

Counts:
- 571 server DATA packets in the 15:08 capture;
- 938 in the 15:12 capture;
- 1,325 in the 15:17 capture;
- These are overlapping counts, **not additive**: the three PCAP files are exact byte-prefix snapshots of the same ongoing recording. The largest v3 file contains **1,325 distinct server DATA/CRYPTO packets**, all with the same 16-byte IV field. The previously quoted total of 2,834 double/triple-counted packets.

The phone-to-peer DATA packets have distinct IV values in the inspected captures.

The public uNabto AES-CBC implementation writes a 16-byte IV using `nabto_random()`. The public repository also contains a clearly marked dummy random implementation that fills the output with the byte sequence 0, 1, 2, ...; its first 16 bytes exactly match the observed server-side prefix.

This is a notable implementation anomaly, not yet a proven vulnerability in the Genvex gateway. The remote endpoint's role and exact firmware/build are not established, and the public source may not be the exact source revision/build used by the device. Do not attempt to exploit this observation, replay packets, or infer that it enables decryption. It should be raised with Nabto/LS Control for confirmation.

## 6. Control-plane handshake observations

At session startup, the capture also contains Nabto control-plane packets:
- `CP_REQ_SP` (type 11) from the phone to two UDP/5566 endpoints, containing SP_ID, CERT, version and capability payloads;
- `CP_REQ_SP` responses containing CERT, NONCE, capability and endpoint-related payloads;
- `CP_CONN_SP` (type 12) request/response packets containing CRYPTO and VERIFY payloads;
- `U_CONNECT` (type 131) rendezvous packets associated with the subsequent peer connection.

The `CP_CONN_SP` crypto payloads use code `0x0016`. In the public uNabto definitions this code corresponds to CRYPT + certificate encryption + PKCS#1 padding. The capture does not reveal the private key or plaintext of these handshake payloads.

This establishes that the DATA exchange is preceded by a separate Nabto control-plane/profile/certificate exchange. It does not identify the current Genvex account provisioning endpoint or prove that Genvex Connect 4.0.3 uses the exact public uNabto revision.

## 7. What is established and what remains unknown

**Established**
- The 70-byte packet is a standard Nabto DATA packet with a CRYPTO payload.
- Its crypto suite is `0x230A` (AES-CBC + HMAC-SHA256).
- Its header, payload and crypto-data boundaries can be parsed.
- Nine fan-change markers across three captures each have a 70-byte request shortly before the manually entered timestamp.
- Each correlated request receives a NOTIFY_MICRO_ACK and a DATA response.
- The 70-byte request's encrypted plaintext is no more than 15 bytes under the published format.
- The responder-side IV-like field is constant across **1,325 distinct DATA/CRYPTO packets in the largest cumulative v3 PCAP** and matches the public uNabto dummy random implementation's output. Earlier `2,834` counts were incorrect because the capture files overlap.

**Not established**
- The plaintext RPC/query name or fan-stage value.
- Whether every correlated 70-byte request is the fan write, or whether some are another operation triggered by the same app action.
- The identity/role of the remote IP endpoint.
- Whether the responder's constant IV is caused by the dummy RNG, a deliberate deterministic implementation, a protocol-version difference, or another implementation detail.
- The exact profile/key provisioning used by the current Genvex Connect app.
